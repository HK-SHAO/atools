# 迁移记录：Bun 构建 → Vite，数值内核 → MoonBit

每一次「换掉底层」都要留下可对照的数字与判据，否则「没有回归」只是一句话。
本文件按里程碑追加，只记**实测**与**决策依据**；原理与管线细节归 `build.md` / `algorithms.md`。

判据分三层，缺一层就不算验过：

1. **等价**：迁移前后同一输入的输出逐位或统计无差别（逐位优先，做不到才退统计并写明分布）。
2. **门禁**：原有的断言一条不少地仍然绿；新增断言必须**故意制造一次违例**确认真能抓到。
3. **消融**：性能与体积有前后数字；被否掉的方案连数字一起留档，避免重复论证。

## 里程碑 1：Vite 替换自建构建与自建服务器

### 删掉了什么

| 文件 | 行数 | 原本做什么 | 现在由谁做 |
| --- | --- | --- | --- |
| `build.ts` | 106 | 两次 `Bun.build`、手推应用壳、算缓存指纹、注入 `__SHELL__` | `vite.config.ts` + `scripts/sw.ts`（构建插件） |
| `src/index.ts` | 29 | 自建 dev 服务器（HMR）与 dist 静态服务器（SPA 回落） | `vite dev` / `vite preview` |
| `bunfig.toml` | 2 | Bun dev 的静态服务配置 | 同上，已无对象 |
| `src/assets.d.ts` | 10 | 手写 `*.ogg` / `*.m4a` 模块声明 | `vite/client` 自带（连同 CSS、PNG、`import.meta`） |

`src/index.html` 上移到仓库根（Vite 的入口约定），静态资源移进 `public/`：`manifest.webmanifest`、
`logo.svg`、`icons/*.png`。这些文件**不经打包器改写**，按字面路径落进 `dist/`，
与 manifest 里 `scope`/`start_url` 的 `"./"` 一致，子路径部署天然成立。
`app/icons/icon.svg`（maskable 图稿源）刻意**留在 `app/`**：它不进产物，挪进 `public/` 就会白带一份。

### 保住了什么

- **应用壳仍是推出来的**：`index.html` 的 `./` 引用 ∪ manifest 自引的图标，取并集排序。
  解码器是动态 import 的独立 chunk，HTML 不引，天然留在壳外。
- **缓存名仍是壳的内容指纹**：名字加每个成员的字节一起喂 `sha256`。改 HTML 标记会换缓存名。
- **壳缺一项、`sw.js` 残留占位符**：两条构建期校验都还在，前者由 `scripts/sw.ts` 抛错，后者是文本替换后的复核。
- **更新语义**：`install` 仍不发 `skipWaiting`，新版停在 `waiting`。

### 产物对照

| 项 | Bun 构建 | Vite 构建 | 差 |
| --- | --- | --- | --- |
| `dist/` 总体积 | 2044 KB | 1544 KB | **−24%** |
| 主入口 chunk | 269.1 KB | 276.1 KB | +2.6% |
| CSS | 7.2 KB | 7.0 KB | −3% |
| `sw.js` | 1.1 KB | 0.86 KB | −22% |

总体积降两成来自压缩器（rolldown/oxc）更狠：解码器分包合计从 1.62 MB 降到 1.14 MB。
入口 chunk 反而略大，是 Vite 的模块包装与预加载辅助代码，量级可忽略。

### 不回归证据

- `bun test`：124 通过 / 0 失败（与基线同数）。
- `bench/offline.ts`：**全部合格** —— 壳逐项 8 项、断网后 html/script/style/manifest 全 200、
  运行期缓存收下演示音频、新版停在 `waiting`、SPA 回落的 HTML 没进缓存、`sw.js` 不在预缓存里。
- `bench/scale.ts`：五档容器宽度全合格，`@property --u` 与 `-webkit-backdrop-filter` 都还在产物里。（该台已于里程碑 6 删除）
- `bench/perf.ts`：通过，重采样倍数 6.6× / 7.2× / 5.5×、相位最多组合 4.37× 起，与基线一致。
- `bench/run.ts`（单素材）：可逆 PNG 相关 1.000 / LSD 0.3、JPEG 相位可靠 0.63、缩放档 degraded，
  与基线逐项一致。
- `tsc --noEmit`：干净。

### 迁移中真实踩到的三个缺陷（都是「绿灯可证伪」的样本）

1. **首屏白屏：`import.meta.hot.data.root`**。`app/frontend.tsx` 原本直接写
   `(import.meta.hot.data.root ??= createRoot(elem))`。Bun 的打包器会把整个表达式折掉，
   Vite 把 `import.meta.hot` 替换成 `undefined`，于是取 `.data` 直接抛错。
   **抓法**：CDP 里 `Runtime.exceptionThrown` 报 `Cannot read properties of undefined (reading 'data')`。
   改成显式守卫（`hot?.data.root ?? createRoot(elem)`）。构建成功、类型干净、单测全绿都没抓到它。
2. **Service Worker 没注册上**。构建期把壳清单塞进了 `JSON.parse(...)` 的槽位，但塞的是**对象字面量**，
   运行期 `JSON.parse` 收到 `"[object Object]"` 抛错，又被注册处的 `.catch(() => {})` 吞掉 ——
   表象是「SW 十秒内没就绪」，不是任何一条显式的错误。
   **抓法**：`bench/offline.ts` 29 项不合格。现在注入的是**双引号字符串字面量**：
   JSON 的转义是 JS 字符串转义的子集，直接可用，也不必理会压缩器原来用的是哪种引号
   （实测 oxc 会把 `"__SHELL__"` 改写成 `` `__SHELL__` ``，按某一种引号去匹配会漏）。
3. **门禁绑死了产物布局**。`bench/scale.ts`（已于里程碑 6 删除）用 `new Bun.Glob("*.css")` 数 CSS 产物，
   Vite 把 CSS 放进 `assets/` 之后它报「一个都没有」，看着像产物坏了，其实是断言写死了扁平布局。
   改成 `**/*.css`：契约是「整个 dist 只有一份 CSS」，产物放在哪一层不是。

### 被否掉的方案

**@vitejs/plugin-react（连 React Compiler）**。`bun add -d @vitejs/plugin-react babel-plugin-react-compiler`
后按官方文档配 `react({ babel: { plugins: [["babel-plugin-react-compiler", {}]] } })`，重新构建 ——
**产物逐字节不变**（主入口 chunk 内容哈希与不接时相同：`index-D4X96kXc.js`）。
代价实测：顶层包 18 → 21、安装体积 38 MB → 45 MB（+3 包 / +7 MB，且这还是 babel 通道未真正挂载时的下限）。
既无可测收益又要多背依赖链，不引。JSX 由打包器原生转换；代价是改组件走整页刷新而非 Fast Refresh，
本项目规模下可接受。真要有意义，理由得是「分析器量到 re-render 成本」，而不是「别家都装」。

> **重测与撤回（工具链整理那一轮）**：上面那次测的是 `react({ babel: ... })` 通道，而那条通道
> **根本没挂载** —— 所以「逐字节不变」量到的是一个空操作，据此否掉它不成立（那半句「这还是 babel
> 通道未真正挂载时的下限」当时就该拦下这个结论）。改用 `@rolldown/plugin-babel` 的
> `reactCompilerPreset()` 之后编译器**确实在跑**：产物里 9 处 `react.memo_cache_sentinel`、
> 6 处 `useMemoCache`，入口 chunk 264 421 → 270 801 B（+6 380 B / +2.4%），而 `react()` 本身
> 仍是零字节（三档构建同轮对照，表在 `docs/build.md`）。结论改判为**接上**。
> 顺带：`+3 包 / +7 MB` 的安装代价仍然成立，只是这次有了对应的收益。

## 里程碑 2：MoonBit 内核骨架接进 Vite

### 与 `sfengine` 的一处刻意分歧：内存不静态定型

sfengine 把 `memory-limits` 钉成 `min=max`，换「宿主缓存的 typed view 永不 detach」，因为它的
缓冲上限是固定网格（约 17 MB）。本项目的缓冲**随素材涨**：像素预算 16M 时，只「目标幅度」一张
`Float64` 表就是 128 MB。手机上开机就要 256 MB 是直接要不到。

所以这里换成另一套契约，写在 `moon/moon.pkg` 里：**按 job 分配 → 全部就绪后取指针 → 再开始计算**。
宿主每个 job 开始时重读一遍地址，`memory.grow` 造成的 detach 就落在契约之外，不靠「禁止增长」保证。
运行期零分配靠的是「中间缓冲在 begin 里一次配齐」，而不是靠禁止增长 —— 这是本设计唯一的软肋，
由「每个 job 只有一次取指针的时机」这条纪律兜住。

### 骨架与构建链

| 文件 | 职责 |
| --- | --- |
| `moon/moon.pkg` | `foreign_library` + `supported_targets = "wasm"`；导出 `memory`，**零 import** |
| `moon/ffi.mbt` | `#borrow` 取 `FixedArray` 数据区首地址、`memory.copy/fill`、v128 访存、裸地址读写（测试用） |
| `moon/engine.mbt` | `dsp_abi` 与 canary 握手；白盒测试证明「导出地址 = 数据区首地址」 |
| `scripts/moon.ts` | mtime 判 stale → `rm -rf moon/_build` → `moon build --release --target wasm`；Vite 插件 |
| `app/lib/dsp.ts` | 加载器：ABI 校验、canary 双向握手、按需切 typed view |

判 stale 后**一律连 `_build` 一起删干净再编**：moon 的增量链接对 `moon.pkg` 变更会失活
（实测导出面残留），全量重编 62~123 ms，换「产物与配置必然一致」很划算。

内核在产物里是**固定名** `wasm/dsp.wasm`，不是内容哈希：它由 `index.html` 的
`<link rel="preload" as="fetch">` 引用，只有被 HTML 引到才会进应用壳 —— 而它必须进壳，
否则「首次访问 → 断网」之后什么也编不了。缓存换代靠的是壳的内容指纹（改内核字节就换缓存名）。

### 实测数字

| 项 | 数字 |
| --- | --- |
| 内核 wasm | 2044 B（骨架期只有握手） |
| 初始内存 | 1 页 / 64 KB |
| import 数 | 0 |
| 编译耗时 | 全量 62~123 ms |
| 应用壳 | 8 项 → 9 项（新增 `wasm/dsp.wasm`） |
| `dist/` 总体积 | 1544 KB → 1548 KB |
| 测试 | 124 → 128 通过（新增 4 条握手/契约断言） |
| dev 重编 | 改 `moon/*.mbt` 后 80 ms 防抖内自动重编并整页刷新（实测 touch 一次 → 62 ms 编完） |

### 门禁与可证伪性

- `app/lib/dsp.test.ts` 4 条：ABI 一致、**导出地址双向握手**（内核写宿主读 / 宿主写内核读）、
  零 import 且导出 `memory`、加载器解析出的 URL 与构建落点同一条路径。
  第一条与第二条盯的是一条**没有文档背书**的 ABI —— 工具链升级若改了 `#borrow` 的传参表示，
  这里会先响，而不是等到某个数值调用给出「看起来合理但不对」的结果。
- `scripts/sw.ts` 新增：**应用壳里必须有 `WASM_FILE`**。
  故意制造违例：把 `index.html` 的 preload 写成绝对路径 `/wasm/dsp.wasm`
  （Vite **不**改写 `rel="preload"` 的 `href`，而壳只认 `./` 开头的引用）→ 构建硬失败
  `应用壳里没有 wasm/dsp.wasm`。这条断言确实抓得到，不是同义反复。
- `bench/offline.ts` 新增：**数值内核必须在预缓存里**。URL 从运行中的 DOM 的 `preload` 取，
  不从构建脚本抄；preload 整个消失时直接判不合格，而不是把这条断言静默跳过。现在预缓存 9 项全绿。
- `bun test` 128/128；`tsc --noEmit` 干净。

## 里程碑 3：FFT 移植 —— 以及一次否定「换语言就更快」的消融

### 移植了什么

`moon/plan.mbt` 一次性算好 `rev` / 旋转因子 / 汉宁窗（三张静态表，`*_ptr()` 导出给宿主），
`moon/fft.mbt` 是原地 radix-2 变换，末级（`step == 1`）单独走 v128 整对打包。
`app/lib/dsp.ts` 的 `planOf()` 把这些表切成熟宿共享的视图，`app/lib/fft.ts` 的 TS 实现原样留在仓库里
**作为参照实现**，逐位比对靠它。

### 等价判据：分成「必须逐位」与「只约束 ulp 上界」两类

一次 FFT 里有两类东西，混在一起谈「逐位等价」是含糊的：

| 量 | 判据 | 实测 |
| --- | --- | --- |
| 位反转置换 | **逐位相同** | 0 处不同 |
| 旋转因子 / 汉宁窗 | ≤ 1 ulp | 1 ulp（相对 2.19e-16） |
| 正/反变换结果 | ≤ 8 ulp | 最大 3.4 ulp |

旋转因子那一项**做不到逐位**：TS 写 `Math.cos(2πi/N)`，V8 的 `Math.cos` 与 MoonBit 的
`@math.cos` 在末位差 1 ulp，这是两个超越函数实现的差别，不是编码错误。
量级上它相对误差 2.19e-16，而数据最终落到 Float32（1.2e-7）与 8bit 幅度（1/255），
相差九个数量级 —— 所以「exact 档逐位不变」这条强断言挪到**产物**上去验，不在这里卡。

`app/lib/fft.test.ts` 9 条，`ULP_BOUND = 8`，窗长扫 256 / 512 / 1024 / 4096。
**故意制造一次违例**：把 `k = k + step` 改成 `k = k + 1` → 门禁报 `6293310820384024` ulp，
确认它抓得住，随后恢复。

### 消融：WASM 内核 vs TS 参照实现，同一台机器、11 轮取中位数

```
  win  256    2,930 次（含 im 清零）   wasm   2.40 µs   TS   2.36 µs   → 1.02×
  win  512    1,302 次（含 im 清零）   wasm   5.33 µs   TS   5.16 µs   → 1.03×
  win 1024      586 次（含 im 清零）   wasm  11.70 µs   TS  11.14 µs   → 1.05×
  win 4096      400 次（含 im 清零）   wasm  55.63 µs   TS  52.84 µs   → 1.05×
```

**结果是否定的：wasm 反而慢 2%~5%。** 四档窗长一致，不是噪声。

原因不神秘：这个内层循环是「定长数组 + 连续常量索引 + 无分配」，V8 的 TurboFan 已经把它
优化到接近标量硬件极限；wasm 那一侧多出来的是**边界内存访问的间接层**，而不是更少的指令。
SIMD 也不是解药：数据是 f64，v128 只有 2 条道，radix-2 蝶形的 cross-lane 代价吃掉全部收益，
实测末级上 v128 与标量持平。

### 顺带把整条链的耗时摸了一遍（8s @ 8kHz，win 512 = 501 帧）

| 环节 | 耗时 | 占比 |
| --- | --- | --- |
| `encode` 完整 | 6.9 ms | 5% |
| `synthesise` 完整 | 135.7 ms | 95% |
| ├ `phaseFromMagnitude`（PGHI） | 8.1 ms | 逆变换的 5.9% |
| └ `rtisiLa`（8 轮） | 106.0 ms | **逆变换的 78.1%** |

**编码侧根本不是瓶颈**（6.9 ms），瓶颈是逆变换里的 RTISI-LA，而它 2/3 的时间又在下述这个格局里：
每帧 `act = K+1` 个槽位、每轮 `act` 次正变换 + `act` 次反变换、共 `iters` 轮。
两处的旋钮是同一个预算：

```ts
const unit = frames * L * max(1, log2(L));
while (K > 1    && unit * (K + 1) * iters > budget) K--;
while (iters > 1 && unit * (K + 1) * iters > budget) iters--;
```

所以**每帧的 FFT 次数不是常数**：2.5s 素材（157 帧）拿到完整的 K=3、每帧 64 次变换；
8s 素材（501 帧）被预算压到 K=1、每帧 32 次。看「每帧多少毫秒」会得出相反结论，
必须换算到**每次变换**：两档实测都落在 5~7 µs/次（含窗乘、重叠相加、`load` 拷贝），与上表的裸 FFT 对得上。

### 这条负结果决定了后面怎么走

「把 TS 数值代码逐行翻成 MoonBit 就会更快」到这里被证伪了。剩下的价值只有三条，各自可证伪：

1. **算法本身的改动**（不是换语言）——RTISI 里那 64 次变换，每一次要么是「实输入 → 复输出」，
   要么是「Hermite 谱 → 实输出」，都够格用**实数 FFT 折半**或**两条实序列打成一个复变换**。
   这是 2× 量级的、与语言无关的收益，必须在 wasm 里做才能顺手拿到 SIMD。
2. **主线程不阻塞**——与语言无关，独立成立，见里程碑 4。
3. **一份实现多处编译**（离线批处理走 native）。

所以后续不把 STFT / 相位重建整段平移，**只把能真正吃到 SIMD 的密集内核搬过去**，
搬一个消融一个。

## 里程碑 4：两条实变换打成一个复变换 —— RTISI 的 FFT 次数减半

### 为什么是这个，而不是继续换语言

里程碑 3 已经量清楚了瓶颈的形状：逆变换里 78% 在 RTISI，其中约八成是 FFT 本身。
而这批 FFT 有个共同点 —— **每一次要么是「实序列 → 复谱」，要么是「Hermite 谱 → 实序列」**。
实序列的谱是 Hermite 的，两条独立变换等于把同一份冗余算两遍。把两条打成
`z = x1 + i·x2` 做一次复变换再拆开（`app/lib/pair.ts`），**变换次数直接减半**，
多出来的只是 O(N) 的加减。这是与语言无关的算法收益，也是里程碑 3 说的那条「让 wasm 有意义的支路」：
只有在 wasm 里才拿得到 SIMD，而 SIMD 要有能吃的循环 —— 打包之后那几圈加减正好是。

### 判据：分两侧，一侧逐位、一侧卡 ulp

| 量 | 判据 | 实测 |
| --- | --- | --- |
| 反变换（第二条喂零） | **逐位相同** | 0 字节不同 |
| 正变换（第二条喂零） | ≤ 4 ulp | 1.31 ~ 2.27 ulp |
| 打包两条 ↔ 两次独立变换 | ≤ 8 ulp | 通过 |
| 正变换 → 反变换回输入 | ≤ 8 ulp | 通过 |

**反变换侧能逐位，是这次改造的回归锚点**：第二条喂零时 `Z = X1`，`inverse` 交给 FFT 的整谱
与 `mirrorSpectrum` 逐项同源同序（连 DC 与奈奎斯特点的置零都落在同一处），所以它必须一模一样地
复现老路。这条钉住了 Hermite 那套约定没写歪 —— 写歪了不报错，只会让直流慢慢飘走。

**正变换侧做不到逐位，这事必须写清楚而不是含糊过去**：打包必然做一次 Hermite 对称化
（`X1[k] = (Z[k] + conj(Z[N-k]))/2`），而老路直接取实信号 FFT 出来的 `Z[k]`。两者在
「实信号」这个前提下是同一个量，浮点上的差就是谱的虚部不对称量的一半 —— 纯舍入噪声，
随窗长 1.31 ~ 2.27 ulp，所以卡 4。**卡 0 会假红。**

### 这次的新发现：RTISI-LA 在这个参数下是不稳的

按老办法「两条支路逐位对照」时，波形差了峰值的 39%。查下去是这个原因：

| 对照 | 中位相对偏差 | 谱差 | 包络 |
| --- | --- | --- | --- |
| 打包 ↔ 不打包 | 1.40e-2 | 3.045 dB | 0.910 |
| 不打包 ↔ 给**同一支路**的幅度喂 1 ulp | 1.08e-2 | 2.819 dB | 0.927 |

**即：给不打包那条支路喂 1 ulp 的幅度扰动，代码一个字不改，输出照样差到这个量级。**
对照组「同输入跑两次」逐位相同（0 个样点不同），所以不是不确定，是**条件数**：
每帧把误差放大百分之几，几百帧后饱和。与 docs/algorithms.md 里记的「RTISI 在粗档是病态的」同源。

结论有两条，都要留下：

1. **这一层的波形级逐位/ulp 对照是无效判据** —— 它对任何重写都会红，对输入扰动也会红。
   所以单元测试改成两条：良态素材上卡死「中位相对偏差 < 1e-12」（打包写错会跳到 O(1)，
   实测故意配错槽位报 1.02，抓得住），以及「两支路对参照的相关差不超 0.05」。
2. **端到端只能按分布比**。15 个用例 × 6 个指标，两条支路的差：

| 指标 | 打包 − 逐条 |
| --- | --- |
| 相关 | 15 项全部 0.000 |
| 包络 | 最大 ±0.002（两项，一正一负） |
| 感知谱距 | 最大 ±0.06 |
| 谱差 / 收敛 | 逐项一致 |

### 消融数字

| 项 | 逐条（`pair:false`） | 打包（默认） | 差 |
| --- | --- | --- | --- |
| `rtisiLa`（8s@8k，win 512，501 帧，iters 8） | 112.2 ms | 65.8 ms | **1.71×** |
| `bun run quality` 整轮（15 用例） | 4.42 s | 3.19 s | **1.39×** |

`--tune='{"pair":false}'` 一行复现过，`TUNE.pair` 当时是那个口。

**这个口已经撤了**：配对后来搬进内核（`moon/pair.mbt`）成了唯一的一条路，「逐条」那条支路
连同 `app/lib/pair.ts` 与 `TUNE.pair` 一起删掉 —— 留着就是一个没人读、也再没人会读的开关。
上面的数字因此是历史读数，不是今天能重跑的口。

### 这次抓到的两个真缺陷（都是门禁抓的，不是人眼看的）

1. **配对时两条共用了一个幅度行号**。`lay` 收到的 `f` 是槽位 0 的行号，槽位 `k` 该读的是
   **第 `m+k` 帧**的幅度。表现是相关性掉三成（0.272 → 0.191）而**所有单测全绿** ——
   是 `bun run quality` 的指标把它顶出来的。
2. **消融口自己写错了**。批大小 `step` 关掉时是 1，但第二个槽位仍按 `k+1` 给，
   于是 `pair:false` 把相邻两帧互相打包、`read` 还顺带覆写下一槽的相位。

## 里程碑 5：数值流水线搬进 Web Worker

### 为什么是 Worker，而不是继续把东西往 MoonBit 搬

里程碑 3 的负结果是「WASM 内核比 TS 参照慢 2%~5%」，里程碑 4 的 1.71× 来自**算法**
（少了一半 FFT）而不是语言。这两条合起来说明这一层的瓶颈不在指令选择上，先别再换语言。
于是照着画像找真正的大块：60s @44.1k WAV 落进页面、走完到出图，CDP Profiler 200 µs 采样，
主线程有效 ~285 ms，最大的两块是原生解码 125 ms 与 `resample` 44 ms。

解码动不了 —— **Worker 里没有 `AudioContext`**。`resample` 是纯函数，且它的相位表缓存
（最坏 4 MB）本来就该住在长期活着的线程里，搬过去反而更合算。

### 边界：什么搬过去了，什么留在主线程

| 事 | 去哪 | 为什么 |
| --- | --- | --- |
| 重采样 | Worker | 纯函数 |
| 编码 | Worker | 纯函数 |
| 还原 | Worker | 纯函数 |
| 出图（紧凑档） | Worker | 纯函数，`spectrumToPng` 不碰 canvas |
| 出图（可逆档） | 主线程 | 要走 canvas 的 `toBlob` |
| 读图 | 主线程 | 要 canvas |
| 解码 | 主线程 | 要 `AudioContext` |

判据是「有没有 DOM 依赖」，不是「重不重」：`app/lib/` 本来就无 DOM，所以搬过去一行算法没改。

### 三条契约，各有门禁

1. **播放与「存音频」走 `synthesise(spec)`**，不是编码前的原声 —— 既有契约。搬进 Worker 后
   返回值是转移过来的 buffer，这条仍然成立。**但守它的界面冒烟台在紧接其后的 bench 删减里
   被移除了**（见里程碑 6），从此只剩人工核对。
2. **参数一变必须作废在飞的活**。取消是**消息式**的：主线程换代次（`generation()`）时
   `scope.cancel()`，Worker 那边每 12 ms 让出一次事件循环，正好来得及读到。取消只作废
   同一个 `scope` 的活 —— 质检与工作台各拿一个，不会互相掐。
3. **Worker 产物必须进应用壳**。它就是断网之后「点转换」的那条路，漏了只在离线时暴露。
   判据见下面的缺陷 1。

### 消融：同一台机器、同一段素材、各跑 3 次

| 项 | 搬之前 | 搬之后 |
| --- | --- | --- |
| 主线程有效占用 | 292 / 278 / 283 ms | 239 / 234 / 239 ms |
| `resample` 自身（采样占比最高的帧） | 44.1 / 44.4 / 44.2 ms | **不再出现在画像里** |
| `bench/perf.ts` 长任务 | 2 个，合计 189 ms | 1 个，合计 128 ms |

搬过去多付的代价是 `postMessage` 的结构化克隆（`pn` / `qe` 各约 6 ms）：`source.pcm`、
`job.spec`、`ref` 这些主线程随后还要用，**不能转移所有权**，只能克隆。拿 6 ms 换 44 ms，
并且那 44 ms 原本是**一口气不让出**的。

剩下那 1 个长任务（128 ms）是原生解码，与本次改动无关：画像里它是 `se`，即 `decodeNative`。

既有门禁：`bun test` 158 通过 / 0 失败，`tsc --noEmit` 干净，`bench/quality.ts` 15 用例不变，
`bench/offline.ts` 全绿（应用壳 **9 → 10 项**，多了 `assets/pipeline.worker-*.js`）。

### 这次抓到的两个真缺陷（都不是人眼发现的）

1. **按 `facadeModuleId` 认 Worker 产物，在 Vite 8 里永远认不出来。** worker 子构建把产物
   当 **asset** 交上来（`type === "asset"`，没有 `facadeModuleId`），入口信息在交上来之前就丢了。
   表现有两层：先是 `worker = ""` 混进应用壳，`readFile("dist/")` 抛 `EISDIR`；更坏的是
   **它把真正的构建错误盖掉了** —— Vite 在渲染阶段失败之后也会走 `closeBundle` 当清理，
   清理时的抛错顶掉了原始错误，于是看不见真因。
   修法：产物名由 `vite.config.ts` 与 `scripts/sw.ts` 共用**一份声明**（`WORKER_FILE`），
   仍然从产物图里推、认不出就当场失败。故意把产物名改掉跑一遍，构建红：
   `产物里以 assets/pipeline.worker- 开头的文件有 0 个…`。
   另外 `closeBundle` 里加了一道「`dist/index.html` 不在就直接返回」，免得清理路径再盖错误。
2. **测量台自己的开销被算进了「长任务」。** `bench/perf.ts` 原来在开表**之后**才合成那 60 s 的
   sin 循环（实测 55~64 ms），于是这项指标永远挂着一个与页面无关的底噪，读数没法用。
   改成先造好素材、再开表：长任务 2 → 1。这条改的是**判据本身**，不改被测对象。

### 顺带量到的一条（下一个里程碑的入口）

`AudioContext` 的默认速率是**设备速率**（headless 实测 48000），`decodeAudioData` 会把 44.1k
的素材悄悄重采样到 48k。同一段 60s WAV：

| 解码上下文 | 耗时 | 输出 |
| --- | --- | --- |
| `new AudioContext()`（48k） | 65 ms | 48000 Hz · 2 880 000 样点 |
| `new AudioContext({ sampleRate: 44100 })` | 17 ms | 44100 Hz · 2 646 000 样点 |
| `new OfflineAudioContext(1, 1, 44100)` | 16 ms | 44100 Hz · 2 646 000 样点 |

即默认路径**既慢 4 倍、又多一次不可控的重采样**（44.1k → 48k → 我们再做 48k → 8k）。
这条留作下一个里程碑：要么按素材原生速率建解码上下文，要么让 WASM 解码器进 Worker
（主线程彻底归零）。两条都得配等价消融 —— 「更快」本身不是换的理由。

## 里程碑 7：解码上下文不再偷换采样率

上一节留下的入口。`decodeAudioData` 把结果重采样到**解码上下文的采样率**，而默认上下文是**设备**
速率（headless 实测 48000），于是 44.1k 的素材先被转到 48k、再由我们转到目标档：多一道不可控的
重采样（65ms 对 17ms），而且界面上的「原声档」拿到的其实是 48k —— 名不副实。

改法就一句：**建上下文时给出素材自己的速率**。难的不是这句，是「素材自己的速率」从哪来。

### 覆盖面：五种读得出，M4A 刻意不读

| 容器 | 速率写在哪 | 谁去读 |
| --- | --- | --- |
| WAV | `fmt ` 块 | `@audio/decode-wav/meta` |
| FLAC | `STREAMINFO` 前 3 字节 | `@audio/decode-flac/meta` |
| OGG | Vorbis 标识头 | `@audio/decode-vorbis/meta` |
| OGG/Opus | 规范规定恒为 48k | `@audio/decode-opus/meta` |
| MP3 | **帧头**（不在 ID3 里） | 自己读十几行 |
| M4A/MP4 | `mp4a` 条目 —— **不可信** | 不读 |

**M4A 不读是有意的。** 它的 `mp4a` 条目在 HE-AAC v1 上写的是**核**速率而不是解出来的速率：
本仓 `he-aac.m4a` 那个字段是 22050，而解码器给的是 44100。照 22050 建上下文，浏览器会先把 SBR
展开到 44100、再为迁就上下文压回 22050 —— 那一道**丢掉整条 11k~22k 的高频带**，比多转一道重采样
糟得多。同一个字段在实际文件里两种写法都有（Apple 系写输出速率），容器自己都没定论，就别猜。

这条边界有测试兜着（`containerRate` 对三个 m4a 夹具必须返回 `null`）。附带的事实：M4A 只在
**原生解得开**时付那道重采样 —— 原生解不开就落到 WASM 兜底，那边解码器自己会报出 44100。

### 顺手删掉的一处重造轮子

原先为了让 WAV 走到这一步，手写了 40 行 RIFF 解析（`wavRate`）外加 4 条单测。而
`@audio/decode-*` 每个包**自带 `meta` 子路径**，`parseMeta(bytes)` 直接给 `{ sampleRate }` ——
同一个作者、同一份格式知识。于是那 40 行连同它的测试一起删掉，换成 6 行分发 + 映射表。
只有 mp3 例外：库的 `meta` 只解析 ID3，帧头得自己看，补十几行（三处保留值当场否掉误判）。

### 消融：同一批素材，改前/改后各跑一遍

`/tmp/probe-real.ts`，无头 Chromium（设备速率 48000），界面切到「原」档，读文件名里回写的 meta。
「容器说」一列是离线用 `containerRate` 读出来的，不依赖浏览器：

| 素材 | 容器说 | 改前 | 改后 |
| --- | --- | --- | --- |
| 真素材转出的 44.1k WAV（`A01_P01.ogg` 的 14s 人声） | 44100 | **48000** | **44100** |
| `tone.wav` | 44100 | 48000 | 44100 |
| `tone.mp3` | 44100 | 48000 | 44100 |
| `tone-vorbis.ogg` | 44100 | 48000 | 44100 |
| `tone.flac` | 44100 | 48000 | 44100 |
| `tone-opus.ogg` | 48000 | 48000 | 48000 |
| `voice/greeting.mp3`（真素材，本就是 48k） | 48000 | 48000 | 48000 |
| `ra2/A01_P01.ogg`（Opus） | 48000 | 48000 | 48000 |
| `audio-examples/kong.m4a`（原生解不开，走 WASM 兜底） | —— | 44100 | 44100 |

后三行是**对照**：容器说的本来就是 48000（Opus 由规范钉死，语音 mp3 也确实录在 48k），改前改后
都该是 48k —— 没有这三行，前五行的 ✓ 就可能只是「碰巧等于设备速率」。最后一行是第五种情形：
`kong.m4a` 改前就是 44100，因为原生解不开、落到 WASM 兜底，那边解码器自己报真速率。
**前五行改前吐出的那五个 48000，没有一个是巧合。**

顺带量到，PNG 体积没有跟着变：真素材 44.1k WAV 612 KB（改后）对 609 KB（改前），tone 系列都在
4~8 KB 之间来回。**但有一条要写清楚**：拿 8 秒 220 Hz 正弦当素材时，改前 11.7 KB、改后 48.5 KB，
差 4 倍 —— 那是退化素材的假象：正弦的谱面只有二十几行有声、其余整片 0，体积由「裙边刚好压在量化
门限哪一侧」决定，同一信号换个采样率就能翻四倍。真实音频上这个悬崖占不到主导，所以这条不当作
结论，只当作「别拿正弦量体积」的备注。

### 可证伪

- 单测 `containerRate`：五种容器的真夹具逐一对上解码器报出的速率；M4A 三个夹具必须 `null`；
  mp3 帧头的三个版本族梯子、三处保留值、以及「ID3 正文里埋一个假同步，必须整段跨过去」。
- 端到端：上面那张表**故意制造一次违例**跑过一遍（把 `decodeNative(data, rate)` 的 rate 写死成
  `null`），第一列五个 ✓ 全部翻成 ✗ —— 表不是恒真的。
- **`bun bench/run.ts` 的语料碰不到这次改动，这一点先说清楚**：`docs/` 下 43 个素材逐个读过容器，
  20 个 mp3 与 16 个 Opus 全都写着 48000（正好等于本机 headless 的设备速率），7 个 m4a 属刻意不读。
  也就是说在这个语料上「按容器建上下文」与「用默认上下文」得到的是**同一个上下文速率**，
  44×10 的矩阵跑一小时也只会拿到一模一样的数。所以只跑了三文件小样本证明评测台本身没被改坏
  （三种容器各一，`errs: (none)`），没有拿它当本次的回归证据 —— 真正证据是上面那张表。
  换到 44100 的设备上就不一样了：那 36 个 48k 素材会第一次拿到**对的**上下文速率，这是同一次
  改动的另一半收益（本次环境测不到，留给设备速率不是 48k 的人）。

### 代价

产物多出 5 个 `meta-*.js`（2.1~2.8 KB，gzip 1.2~1.3 KB），都是**懒加载**：只有真的落了对应容器的
文件才去取。应用壳仍是 10 项（壳只收入口、产物 HTML 引用与 manifest 图标，动态 chunk 不入壳）。
主 chunk 266.01 → 266.31 KB（+0.3 KB，就是那段分发）。

## 里程碑 8：目录改名 `src/` → `app/`（2026-09-11，9638149）

纯改名 + 引用同步。理由：这个目录放的是应用本身（入口、组件、样式、SW），与 `moon/`（内核源）、

## 里程碑 10：测试链换成 vitest，评测台不再自带打包器（2026-09-11）

### 单测：`bun test` → `vitest`

11 个测试文件的 `bun:test` 改成 `vitest`（matcher 完全兼容，一处都不用改写法），
`package.json` 的 `test` 改成 `vitest run`。两处不是换个导入就行：

- `audio.test.ts` 用 `Bun.file(...).arrayBuffer()` 读夹具 —— 换成 `node:fs/promises` 的 `readFile`，

- 一处 `expect(promise).rejects.toThrow(...)` 没 `await`：bun 会替你等，vitest 会**判失败并说明原因**。

（`bench/quality.ts` 是不经浏览器的纯数值消融，但它印的是给人看的表而不是红/绿断言，同样留着。）

`bench/run.ts` 原本用 `Bun.build` 把 `bench/entry.ts` 打成 `bundle-<PORT>.js` ——
那是仓库里的**第二个打包器**，它的转换语义与真应用产物不一致时，差异会悄悄混进指标里。
改用 Vite 的编程式 `build({ configFile: false, write: false, lib: {...} })`，产物照旧落盘
（`serve.ts` 是另一个进程，只能从文件读）。

消融：同一批素材、同样两个用例，只换打包器，两次的 SNR / 相关 / 收敛 / LSD / 幅度 / 层级偏差 / 认图 /
相位可靠**逐项相同**，PNG 体检的五个字节数也一字不差（仅耗时读数有别，那是机器噪声）。
`errs: (none)`。

## 里程碑 11：内核热循环改用 `unsafe_*`，内核自己有了 test 与 bench（2026-09-11）

`moon test --target wasm` 与 `moon bench --target wasm` 立起来了（`bun run test:kernel` /
`bun run bench:kernel`，moon 的定位与错误文案复用 `scripts/moon.ts`，不在 package.json 里再写一遍裸 `moon`）。
白盒门禁落在 `moon/fft_wbtest.mbt`：往返一致、直流能量落第 0 根、Parseval 三条不变量 ——
它们**不需要 TS 参照实现**就能判「算法写错了」。可证伪性当场验过：把 `rj - tre` 改成 `rj + tre`，三条全红。

真正的收获是把内核从「比 TS 慢」翻成「比 TS 快」。里程碑 3 量到裸 FFT 的内核版**慢 2%~5%**，
当时归因于「只搬能吃到 SIMD 的密集内核」。这次把 WAT 翻出来看，原因完全是另一回事：

```wat
(call $moonbit.check_range (idx) (i32.const 0) (i32.sub (call $moonbit.array_length arr) (i32.const 1)))
```

`arr[i]` 编译成**两次不内联的调用**。一次蝶形 8 处读写 = 16 次调用，于是同一份算法慢 7 倍。
`arr.unsafe_get(i)` / `arr.unsafe_set(i, v)` 之后反超 1.5 倍（表见 `docs/algorithms.md`）。

这条与 SIMD 无关，也不是「换语言就更快」的反面 —— 它说明**换语言之后还得看这个后端把下标编成了什么**。
上一次消融得出「只搬密集内核」，这一次得出「搬过去之后热循环不许写下标」，两条都是可证的，不冲突。

副产物：`moon bench` 立起来了，可以当回归锚点。（当时顺手写的「与 V8 里独立量的数字吻合」**是错的** ——
那次是拿内核侧填数去对 JS 侧填数，各带一份不同开销凑巧对上。见下面里程碑 12 的归因。）

## 里程碑 12：票根整段搬进内核 + `moon bench` 的读数归 `moonrun`（2026-09-11）

用户这轮的判断是「绝大多数功能都是无头的，vitest 187 条而 moon test 只 8 条，这个分布不对」。
对，但**不是把用例搬个地方就完了**：测试跟着实现走，实现不在内核里，用例就没法搬。
所以这一轮先立**迁移的固定动作**，再按它搬了第一个整模块。

**迁移的固定动作**（模板：`moon/stub.mbt` + `moon/stub_wbtest.mbt` + `app/lib/stub.test.ts`）：

1. 实现搬进内核，宿主侧只留一次「搬数据」（`dsp_stub_paint` 直接按裸地址把 `w × 8` 的 RGBA 写进
   作业区，宿主一个像素循环都不写，只剩一次 `set`）。
2. 尺寸表与失败语义都在导出面里：`dsp_stub_paint_words(w)` 由内核算，**宿主不自己算布局**；
   容量不够/参数非法一律返回 0，宿主据此退回参照实现 —— 降级，不是崩。
3. 行为断言搬进 `moon/*_wbtest.mbt`（票根那 5 条原在 vitest，整批搬来，另补 2 条只有内核
   才谈得上的：CRC 真拦得住坏位流、三档宽度前缀各自往返）。
4. vitest 那侧只留**一条 A/B 等价门禁**：摘掉内核跑同一批输入，两条路逐字节相同。
5. 每个 A/B 配对都钉住「内核走了一次、参照走了一次」。作业区拿不到、池满、参数越界都会**静默**
   换路 —— 少了这条，一整遍「内核」用例会退化成「参照 == 参照」而照样全绿。

**这五条里有两条的措辞只属于迁移期间**，它们的前提是「参照实现还在」。全部模块搬完之后参照实现
整段删掉：第 2 条的**降级语义**换成「拿不到内核就当场抛」（`dsp.ts` 的 `mustKernel`），
第 4 条的 A/B 门禁换成整链实时倍率与真页面链门禁（里程碑 13 §7）。模板本身没变：
**实现先搬进内核、测试跟着搬、宿主只留一次搬数据**。

**A/B 门禁的价值是当场证过的**，三次注入各跑一遍：① 改 TS 参照的 `DARK` 20→21 →
`drawStub`/`stubLuma` 红；② 改**内核**的 `stub_light` 230→231 →**内核白盒 33 条全绿**
（它的解码是按门限来的，对亮度值不敏感），而 A/B 红 —— 这条信息只有 A/B 有；
③ 把 `dsp_stub_paint_words(w)` 故意撑过上限 → 计数守卫报「内核那条路没走」。

**顺手抓到一个真缺陷：判据与实际不一致。** `stub_fits` 原本是 `w >= span(w) + 4`，
而解码侧的门是「剖面长度 ≥ 46」—— 于是 39~45 这一档「判据说装得下、画了 8 行条码、永远读不回来」。
反过来 `+4` 那个余量又太严：位宽跳档处有两档（70/71）明明能读回来却被拒。
现在两处**共用同一个 `stub_min_decode = 46`**，且门槛取**恰好**的线（`span + 2`，与 `stub_paint`
同一道线）。新门禁是**规则**不是清单 —— 逐宽度画一遍认一遍，要求
「`stub_fits` 说装得下 ⟺ 那个宽度真的认得回来」，报出第一个不一致的宽度。
注入 `+ 2` → `+ 6` 当场红（`first_bad = 70`）。

**`moon bench` 的读数归 `moonrun`。** 里程碑 11 那句「两个来源复核一致」是错的，
这一轮用「**同一份产物换引擎跑**」把它钉死：`moon bench` 的产物也导出全部内核函数，
所以在 V8 里能按同样的姿势量同一个函数。三条排除 ——

- 不是产物差异：应用产物在 V8 里 2.81 / 28.62 µs，`-test-mode` 的 bench 产物在 V8 里 2.83 / 28.60 µs。
- 不是框架开销：`it.bench` 的「闭包 + `keep`」实测 17 ns（新增的 `harness-noop`）。
- 不是填数：新增的 `fill-*` / `forward-alone-*` 拆开了它（512 点：4.31 = 0.35 + 3.97）。

剩下就是引擎：**v128 密集的差 1.4×、纯访存整数的差 1.1×**（表与复现脚本见
`docs/algorithms.md` 的「`moon bench` 的读数归 `moonrun`」与 `bench/moonebench.ts`）。
所以 `moon bench` 只当**同运行时的前后回归锚点**，「内核比 TS 快多少」一律看宿主侧 A/B。

**边界没变的那些**（里程碑 8 已定案，这轮复核过一遍，不重复论证）：`resample`、`png` 都不搬。
留作下一步的是**整条 `encode`/`invert` 连 padding 一起搬** —— 这一轮已经把它的入口收口了：
宿主的 `Frames` 改成占内核的会话槽（`app/lib/stft.ts`），每帧 FFT 与窗都不再出自宿主，
那个 TS `FFT` 类随之删掉（见里程碑 13）。

## 里程碑 13：宿主侧再没有数值实现（2026-09-11）

三件事一起做的，因为它们是同一条链：**宿主最后一处 FFT 进内核**、**两个线程各挂一份内核**、
**解码不再建昂贵的设备上下文**。

### 1. `fft.ts` 删掉，窗与变换都问内核

宿主的 `Frames` 原先自己持有一份汉宁窗表与一张旋转因子表（`app/lib/fft.ts` 的 `FFT` 类），
与内核里的是同一条式子 —— 于是「内核做变换时用的窗」与「宿主加权时用的窗」迟早分家，
症状是数值对不上却谁都没改过错。现在 `Frames` 占内核的一个会话槽（`moon/session.mbt` 的池），
窗直接取表组里的那一张（`planOf(dsp, win).hann()`），`app/lib/stft.ts` 只剩骨架、没有一条数值式子。

内核侧补了 `dsp_real_ifft`：一次完成「单边谱 → 共轭对称整谱」的翻转 + 复反变换。
分成两次调用（先翻转、再反变换）就等于把 DC / 奈奎斯特的虚部置零这一步留在宿主，
漏掉的后果是上半谱带着上一帧的时域样本被当成本帧的谱再变一次 —— 帧 0 之后整条输出都错，
而症状离出错点很远。导出面因此从 ABI 5 升到 6。

**可证伪**（白盒，`moon/fft_wbtest.mbt` + `moon/plan_wbtest.mbt`，逐条注入违例各跑一遍）：
删掉翻转循环 → 2 条红；改蝶形符号 → 5 条红，且各自独立。

同时删掉一条**假门禁**：原先「变换与 TS 参照逐位等价」的 ulp 断言。绝对误差按
`eps·log₂n·Σ|x|` 增长（256 点约 60 ulp），而写错的实现相对误差是 1e-2 量级 ——
判据改成**相对峰值 1e-12**，量级差着十个数量级，才真的分得开对错。

### 2. 真缺陷：主线程那一侧没人挂内核

**症状**：真页面里拖进一张频谱图 → 点「质检」，`.facts` 停在采样率那一行不动，
控制台一条 `Error: 数值内核还没挂上`，报错点是 `stubFits`（离出错点很远）。

**根因**：读图链住在主线程（要 canvas 与 `getImageData`），出图链的紧凑档也在主线程，
而它们每一步都要问内核要票根 —— 但内核只在 worker 里挂了。wasm 实例不跨线程，
所以那一份救不了主线程。**此前没有任何门禁覆盖这条链**（单测里是手工 `attachKernel`，
评测台 `entry.ts` 自挂一份，两条路都绕开了它）。

**收口**：`startKernel(source, { fft })` 是每一侧的启动入口（同一线程只加载一次），
要用内核的异步入口各 `await kernelReady()` 一次（用户的动作是毫秒级的，wasm 还在路上）。
主线程那一份 `fft: false` —— 它只用票根编解码（纯整数），不建 FFT 的表组。

代价量过：44 KB 的模块，真 Chrome 里 fetch 1 ms（preload 已预热）、实例化 0~1 ms、内存 1.25 MB。
**两个线程各挂一份不是双重实现** —— 源码只有 `moon/` 那一份，是同一份实现被实例化了两次。

**门禁**（三条，都注入违例验过）：

| 门禁 | 位置 | 注入什么会红 |
| --- | --- | --- |
| `startKernel` 只加载一次、`kernelReady` 真的等到挂上 | `app/lib/dsp.test.ts` | 把 `??=` 改成重新加载；把 `kernelReady` 改成空操作 |
| 紧凑档出图端到端（不手工挂载） | `app/lib/image.test.ts` | 去掉 `startKernel`；去掉 `spectrumToPng` 开头的 `kernelReady()` |
| 真页面 演示 → 质检 → 重建相位，零异常 | `bench/ui.ts`（新） | 只挂 worker 那一份（就是上面那个原始缺陷） |

`bench/ui.ts` 是常驻门禁而不是一次性脚本：`.facts` 要出现「还原度」且三个标签齐全，
页面零异常、零 `console.error`；长任务只报数（同 `perf.ts` 的理由）。
当前基准：演示就绪 ~0.5 s、全程 **0 个**长任务。

### 3. Worker 与内核都提前起

`pipeline.ts` 改成**模块被引入就建 Worker**（原来等第一次 `send`）。它启动时要编 wasm、
建三档窗长的表组、做掉必然那一次 `memory.grow` —— 三件事只发生一次，但没有一件该落在
用户第一次点「生成」的那一刻。主线程那一份与它**并行**加载，谁先要谁不等谁。

### 4. 解码上下文：`AudioContext` → `OfflineAudioContext`（本轮最大的一笔卡顿）

里程碑 5 顺带量到过「默认路径既慢 4 倍、又多一次重采样」，但那张表量的是**解码**。
它的第一行 `new AudioContext()` 65 ms 里其实压着另一笔账。本轮核实（同一页面内连续建）：

| 构造 | 第 1 次 | 第 2/3 次 |
| --- | --- | --- |
| `new AudioContext({ sampleRate })` | **138 ms** | 0 ms |
| `new OfflineAudioContext(1, 1, sampleRate)` | 0 ms | 0 ms |

**贵的是页面里第一次建设备上下文，不是解码。** 而它落在哪儿？就落在用户点「演示」或
拖进第一个音频文件那一下 —— 实测「演示」那一下主线程一个 159 ms 的长任务，`perf.ts` 的落 WAV
那半报 117 ms（整链 273 ms）。改用 `OfflineAudioContext`：

- **逐样点等价**：同一份 ogg 在 8000 / 44100 / 48000 三档，`AudioContext(rate)` 与
  `OfflineAudioContext(1,1,rate)` 解出的 PCM **0 个样点不同**，长度与返回速率也都一致。
- 语义本来就更对：解码不输出声音，不该去碰音频设备，也不该受自动播放策略约束。
- 它**没有 `close()`**（`typeof close === "undefined"`），也不需要 —— 缓冲随引用回收。
- 结果：演示就绪 846 ms → 512 ms，长任务 159 ms → **0 个**；落 60s WAV 链 273 ms → 159 ms。

**代价要认**：容器里读不出速率时（`M4A/MP4` 是主要的一类）不再拿「设备速率」，改用定值
`DECODE_RATE = 48000`。于是这类文件在「原」档下拿到的速率跟着变 —— 但两边都不是素材的真实
速率，而换来的是「同一个文件不再随机器变」。顺带把 `SR_MAX` 从 192000 收到 96000：
与 `OfflineAudioContext` 能接受的窗口同一个数，一个边界只有一个地方写（超出窗口的值
过去也只能落到默认路径）。

### 5. 顺手删掉的两处死物

`TUNE.pair` 的读取方一个都没有：配对搬进内核（`moon/pair.mbt`）之后成了唯一的一条路，
「逐条」那条支路连同 `app/lib/pair.ts` 一起删了，只剩开关和它的注释留在 `phase.ts` 里
（还指着那个已删的文件）。同批删掉 `moon/pair.mbt` 头注释里对 `app/lib/pair.ts` 的引用，
`docs/migration.md` 里程碑 4 那两处说明也标注了口已撤。

### 6. RTISI 整段搬进内核，连工作区一起

`moon/rtisi.mbt` 现在是唯一实现，宿主 `app/lib/rtisi.ts` 只做三件事：上传 `mag` / `warm` / 频带表、
分块推进（`dsp_rtisi_run` 按 `from` / `to` 推进，推进之间让出）、收尾（`dsp_rtisi_finish`）。
偏移与长度一律问内核要（`dsp_rtisi_off` / `dsp_rtisi_len`），宿主不自己算布局。
白盒在 `moon/rtisi_wbtest.mbt`，内核自基准在 `moon/rtisi_bench_wbtest.mbt`。

同批把内核的工作区换成**作业区**（`moon/arena.mbt`）：一个 handle 同时要两段 —— Double 主缓冲
与 Byte 段（`dsp_job_open(words, bytes)`），取代原先「按 job 分配」。理由不是整洁：
`memory.grow` 会把宿主先前切出的 typed view **全部** detach，而并发是常态（`encode` 与 `synthesise`
分属不同 scope，会在同一个 worker 里重叠），所以「持有一份内核内存上的视图」必须从结构上写不出来。

这次移植留下的教训只有一条，但很值：**同一份内核 RTISI 在自建探针形状（无 band / iters 8 /
有 warm）快 1.29×，在产品紧凑档（带幅度软约束）却慢 12%~24% —— 胜负随配置翻符号。**
当时把它列为「未定案」（待做 band on/off 二分）。现在这条 A/B 已经没有意义了：参照实现整段删掉，
比值门禁随之作废（见下节）。留下的是那句话本身 —— **任何「快了多少」都只能在产品真实配置上量。**

### 7. 整链时间门禁换口径：A/B 比值 → 实时倍率

参照实现删光之后，「内核比 TS 参照快多少」这条 `bun run kernel` 门禁**失去了第二个操作数**：
它是作废，不是通过。重写成**单路实时倍率** —— `总耗时 / 音频时长`，它不依赖谁的实现更快，
只依赖「比播放快多少」，而后者才是「操作不要卡」这句话的可判形式（门禁 `RT_GATE = 0.05`）。
数值侧另挡「跑着但结果是垃圾」：NaN / Inf 与整条全零都能悄悄通过时间门禁。

30 s 素材实测：

| 档位 | 重采样 | 编码 | 还原 | 合计 | 实时倍率 |
| --- | --- | --- | --- | --- | --- |
| 省 win256 | 20.3 ms | 17.9 ms | 167.4 ms | 205.6 ms | 0.007× |
| 中 win512 | 13.2 ms | 16.6 ms | 138.4 ms | 168.1 ms | 0.006× |
| 细 win1024 | 13.2 ms | 18.3 ms | 121.3 ms | 152.8 ms | 0.005× |
| 细 精确档 | 13.2 ms | 75.6 ms | 18.1 ms | 106.9 ms | 0.004× |

比实时快约 140~250 倍。这张表也顺带说明「省档最慢」不是笔误：`hop = win/4` 下省档每秒列数最多，
RTISI 要推进的帧数也最多；精确档不跑 RTISI（它存相位），还原因此只要 18 ms。
